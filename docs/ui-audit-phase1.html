2Audit findings

Against the brief's own checklist. Marked already good where true — not padding the list, since claiming false gaps would waste implementation effort on non-problems.

real bug
Badge tone colors: incomplete token migration
primitives.css's .badge-positive/.badge-warning/.badge-risk border colors are still the pre-redesign rgba() values (old muted teal-era tones), missed earlier because that pass only grepped for #hex literals, not rgba(). Badge is the most-reused component in the app (category tags, filing-status pills, party pills) — this is visible inconsistency on nearly every screen.
real gap
Information hierarchy: no dominant element on Overview
"Total risks / Average severity / Buried risks / Litigation cases" render as four equal-weight StatTiles. The brief is explicit: the user should see overall risk level first and it should be visually dominant. Right now it's one of four same-size boxes — exactly the "every card looks equally important" anti-pattern named in Phase 3.
real gap
Motion is functionally absent
Every transition in the codebase is a hover-state color/border change. Zero: page/section entrance, number count-up on StatTile values, chart transitions, command palette open/close (currently a hard if (!open) return null cut), success feedback after a completed upload (silently redirects), or choreographed loading→content handoff. This is where GSAP has a genuine, well-scoped job to do — not decoration, actual missing feedback.
partial
Upload pipeline progress feels mechanical
A single rotating text line + spinner over ~1-2 minutes of real backend work (6 pipeline steps). A step-indicator (which stage is active/done) would read as more deliberate and give the user actual position feedback, not just "something is happening."
partial
Empty vs. error states share one visual treatment
EmptyState is reused identically for "no data yet" and "request failed" (e.g. active-IPO list). Differentiating icon/accent color (error → risk-tinted) would help users distinguish "nothing here" from "something broke" at a glance.
already good
Accessibility baseline
Global :focus-visible ring, role="tablist"/"tab"/"listbox"/"option" used correctly, keyboard nav in the command palette (arrows/enter/escape) and risk rows (enter/space), aria-label/aria-expanded/aria-selected throughout, color never used alone (severity always pairs a dot + text label). This was not a weak starting point.
already good
Responsive behavior, icons, gradients/glassmorphism/glow, radius consistency
Mobile bottom-tab-bar + grid collapse + contained table scroll landed last turn (verified via actual scroll-capability testing at all 4 required breakpoints). Icons are Phosphor-only. Zero gradients, zero glassmorphism, zero glow anywhere in the codebase — the brief's most-repeated anti-pattern list is already clean.
worth doing
Chart polish: gridlines, legend, axis treatment
Functionally solid (dark tooltip, muted axis text, tabular nums already applied). Room for a more "terminal" feel — faint gridlines, tighter legend integration — moderate polish, not a structural fix.

3Three.js recommendation: don't

Not recommending Three.js for this product

There's no meaningful 3D opportunity here that a well-encoded 2D chart doesn't already serve better. "Risk landscape" as a 3D scene would read as exactly the gimmick the brief warns against — a serious analyst reading a DRHP risk register wants to scan a table fast, not orbit a scene. The severity donut, category bar chart, and delta-bar peer comparison already give risk visual meaning without asking the user to interact with a camera. This is the brief's own Phase 8 test applied honestly: "only if it genuinely improves the product" — it doesn't here. Flagging this explicitly rather than silently skipping it, since it was explicitly requested as a tool to consider.
